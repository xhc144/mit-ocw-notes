# Connected GitHub fallback (agent workflow)

Use only when the environment lacks usable native Git execution/transport, not when GitHub explicitly refuses access. This is an orchestration playbook for the already connected GitHub tools, not a second independently implemented network client. This release's automatic checkpoint/retry runtime is the native uploader; connected-app orchestration requires the agent to persist each stage and inspect returned results. It has not been exercised as a production upload in this release.

1. Inspect the connected app's exact tool schemas and harmless repo read. Verify exact full_name, active private visibility, write permission, existing branch and HEAD. Keep all existing permissions/endpoints. No token creation, credential extraction, new login flow or refusal bypass.
2. Freeze the exact authorized manifest and safe input snapshots once. Apply the same relative-path, duplicate/prefix, symlink and credential checks as the native workflow. If Python/POSIX is available but Git is absent, use `scripts/connector_manifest.py` for local freeze/plan; it never performs an upload or generates a successful-upload receipt. Otherwise the agent must establish equivalent verified local bytes before invoking mutation tools.
3. Read the complete current remote tree. Handle recursive-tree truncation by enumerating subtrees; do not infer absent paths from truncated data. Reject symlink/gitlink targets or parent collisions and detect LFS/rule changes. Preserve untouched tree entries, executable modes and complete history. Do not edit `.gitattributes`, `.lfsconfig`, `.gitmodules` or credential paths.
4. Compute each frozen file's Git blob SHA from `blob <size>\0<bytes>` and SHA256. Compare the existing target content, skip matches and reuse identical content objects across target paths. Download/read the actual remote selected blobs to verify SHA256/size as necessary. A returned blob SHA must match the frozen expected SHA. Blob creation alone is preparation.
5. Upload missing blobs with the connector's `create_blob`, initially serially (limit 1; never exceed 2). Persist successful SHA mappings after each file/object. A failed file restarts its complete request. Neither API blob calls nor this workflow promise partial-byte continuation. Respect rate-limit headers and bounded exponential retries on 429/5xx/timeout. After an uncertain blob result, read/check that object before recreating it. Never retry explicit denials.
6. With all blobs confirmed, create one tree based on the actual base tree, then one commit whose parent is the inspected head. Serialize tree, commit and ref updates across all branches. Reinspect head/private repo before updating one branch ref with `force=false` and the provider's expected-head guard if available. A conflict requires reading the new head and review, not force or silent overwrite.
7. On uncertain ref update, read the branch before another write. If it already points at the candidate, verify it. If it still equals the expected base, a bounded retry of the same candidate may be considered; otherwise stop. Blob/tree/commit objects may remain even if no ref was updated.
8. Fetch the actual ref, commit, complete selected remote tree/blobs, and hash every selected file. Validate commit parent/base tree, retained untouched entries and modes. Require actual ref==candidate and all SHA256/size matches before success; recheck head after verification. A restored checkpoint also checks remote objects; do not count cached blob mappings as uploaded files.

Checkpoint fields for agent orchestration: immutable manifest_id/repo/branch/expected_head, snapshot path and SHA256/size per file, observed_base_tree, expected/confirmed blob SHA mapping, candidate_tree/commit, ref_update_attempted, last_error, verified_ref and verified file hashes. Do not put credentials or contents in progress logs. Keep state outside Git and preserve it on uncertain completion.

Primary protocol references: [Git push](https://git-scm.com/docs/git-push), [GitHub API best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api), [large file limits](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github). Checked 2026-10-08. These guide the workflow and do not prove an individual upload succeeded.
